ความสามารถหลัก

ฝั่งผู้ใช้

  • จองได้สองทาง: กรอกฟอร์ม (ชื่อ ทีม วันที่ สาขา — ไม่มีช่องบริษัทแล้ว) หรือกดวันบนปฏิทินแล้วกรอกทีละขั้น 3 ขั้นตอน
  • เลือกทีม “Other” แล้วพิมพ์ชื่อทีมเองได้ ระบบเก็บเป็นข้อความที่พิมพ์จริง
  • ปฏิทินทั้งเดือนบอกสถานะทุกวันด้วยสี: ว่าง · ใกล้เต็ม · เต็ม · เต็มและมีคิวสำรอง · วันที่ผ่านไปแล้ว
  • วันไหนเต็ม 15 คิว ระบบจะถามว่าจะลงคิวสำรองไหม โดยต้องกรอกอีเมลไว้สำหรับแจ้งเตือน
  • เลือก Account Number เองได้ จากเลขที่ว่างในวันนั้น เห็นชื่อเจ้าของจริงประกอบ พร้อมระบบแนะนำเลขที่ตรงกับชื่อเล่น/ชื่อเต็มให้อัตโนมัติ และมีข้อความเตือนให้เลือกชื่อที่ตรงเพศ
  • ถ้าเลขที่เลือกถูกคนอื่นจองชิงไปพร้อมกัน ระบบจะแจ้งและเปิดให้เลือกเลขใหม่ทันที ไม่ปล่อยให้ซ้ำ
  • ยกเลิกคิวเองได้ โดยต้องกรอก Account Number ที่ได้รับเพื่อยืนยันว่าเป็นเจ้าของคิวจริง
  • ค้นหาด้วยชื่อ เพื่อดูว่าคนนั้นจองวันไหนไว้บ้าง

ข้อมูลประกอบและระบบหลังบ้าน

  • หน้าคู่มือเต็มจอ สอนวิธีเข้าสู่ระบบด้วยอีเมล วิธีขอรหัส Wi-Fi และขั้นตอนจองห้องประชุม
  • หน้ารวมสาขาแยกตามโซน กดดูแผนที่ของแต่ละสาขาได้ในหน้าเดียว
  • สาขาที่ยังไม่เปิดใช้งาน (8 สาขา) ถูกซ่อนจากแท็บเลือกสาขาไปเลย ไม่ใช่แค่กดจองไม่ได้เฉย ๆ แบบเดิม
  • ดึงข้อมูลใหม่จาก Google Sheets ทุก 60 วินาที ทุกคนจึงเห็นคิวตรงกัน
  • พอมีคนยกเลิก ระบบจะเลื่อนคนแรกในคิวสำรองขึ้นมาเป็นคิวจริงและออก Account Number ให้เลย
  • ส่งอีเมลอัตโนมัติเฉพาะตอนมีคนลงคิวสำรองใหม่ หรือคิวสำรองได้เลื่อนเป็นคิวจริง — คิวที่ยืนยันตั้งแต่แรกไม่มีอีเมลอัตโนมัติ (แต่กดขอให้ส่งเองได้ทีหลัง)

เทคโนโลยีที่ใช้

ตัวหน้าเว็บ

  • เป็นไฟล์เดียวจบ เปิดในเบราว์เซอร์ได้เลย ไม่ต้องติดตั้งหรือคอมไพล์อะไร
  • เขียนด้วยเครื่องมือพื้นฐานล้วน ไม่ได้พึ่งเฟรมเวิร์กสมัยใหม่ตัวไหน จึงแก้ไขต่อได้ง่าย
  • ยืมส่วนประกอบสำเร็จรูปจากภายนอกสามอย่าง: ตัวจัดหน้าตา ปฏิทินภาษาไทย และชุดไอคอน
  • ใช้ฟอนต์ Sarabun ทั้งเว็บ
  • รูปในคู่มือแยกเป็นไฟล์ภาพจริงในโฟลเดอร์ images/ แล้ว ไม่ได้ฝังเป็นข้อความ base64 ในตัวไฟล์เหมือนเดิม

ที่เก็บข้อมูล

  • Google Sheets แท็บ “Booking” เป็นฐานข้อมูลการจอง เก็บทั้งชื่อ ทีม (รวมช่อง “ระบุเอง” เวลาเลือก Other) วันที่ Account Number สถานะ และเวลาที่ทำรายการ
  • มีแท็บ “AccountNumber” แยกต่างหาก เป็นทะเบียนอ้างอิงว่าเลขไหนเป็นของใคร (ชื่อจริง/ชื่อเล่นไทย-อังกฤษ)
  • มีตัวกลางคอยรับคำสั่งจากหน้าเว็บ แล้วไปอ่านหรือเขียนชีตให้ (Google Apps Script) — ต้องแนบรหัสลับทุกคำขอ
  • เบราว์เซอร์จำข้อมูลล่าสุดไว้ในเครื่อง เพื่อให้หน้าเว็บแสดงผลได้ทันทีโดยไม่ต้องรอโหลด

ระบบอัตโนมัติ

  • n8n รับคำขอเฉพาะตอนมีการลงคิวสำรองใหม่ หรือคิวสำรองได้เลื่อนเป็นคิวจริง แล้วส่งอีเมลผ่าน Gmail
  • มีไฟล์เตรียมบอท Discord 2 ตัว (จองผ่านแชท + ส่ง DM แนะนำตัว) แต่ยังไม่ได้เปิดใช้งานจริง และไฟล์ทั้งสองมี credential จริงอยู่ข้างใน จึงถูกกันไม่ให้ขึ้น GitHub
  • ซอร์สโค้ดเก็บไว้บน GitHub แบบสาธารณะ (public repo) — เว็บจริงรันอยู่ที่ GitHub Pages

ขั้นตอนการทำงาน ก่อน – หลัง

เปรียบเทียบกระบวนการจองคิวก่อนมีระบบ กับหลังใช้ระบบนี้

ก่อน — ทำมือผ่านแอดมิน Manual
  1. พนักงานทักแชทหาแอดมินเพื่อขอจองวันและสาขา
  2. แอดมินเปิดไฟล์ตารางเช็กเองว่าวันนั้นเต็ม 15 คนหรือยัง
  3. แอดมินพิมพ์รายชื่อลงตารางด้วยมือ เสี่ยงพิมพ์ผิด/ตกหล่น
  4. แอดมินเลือก Account Number ที่ยังว่างของวันนั้นเอง และต้องจำไม่ให้ซ้ำ
  5. ส่ง Account Number กลับให้พนักงานทีละคนในแชท
  6. ถ้าเต็ม ต้องจดคิวสำรองไว้เอง แล้วไล่ทักกลับเมื่อมีคนยกเลิก
  7. พนักงานไม่เห็นภาพรวมว่าวันไหนว่าง ต้องถามแอดมินทุกครั้ง
หลัง — พนักงานจองเองผ่านเว็บ Automated
  1. พนักงานเปิดเว็บ เห็นปฏิทินทั้งเดือนว่าวันไหนว่าง/ใกล้เต็ม/เต็ม ทันที
  2. กรอกชื่อ ทีม เลือกวันและสาขา แล้วกดยืนยัน
  3. ระบบตรวจกฎเองทั้งหมด: วันย้อนหลัง เกิน 1 เดือน ชื่อซ้ำในวันเดียวกัน โควตา 15 คิว
  4. เลือก Account Number เองจากเลขที่ว่างวันนั้น เซิร์ฟเวอร์ตรวจซ้ำให้ก่อนยืนยันจริงเสมอ
  5. แสดงบัตรคิวบนหน้าจอทันที คัดลอกได้ และเลือกส่งเข้าอีเมลได้เอง
  6. ถ้าเต็ม ระบบเสนอคิวสำรองให้ทันที และเลื่อนคิวอัตโนมัติเมื่อมีคนยกเลิก
  7. ทุกแถวเขียนลง Google Sheets ให้แอดมินดูย้อนหลังได้ตลอด

ผังการทำงานของระบบ

เส้นทางของข้อมูลตั้งแต่ผู้ใช้กดจอง จนถึงการบันทึกลง Google Sheets และการส่งอีเมล

การอ่าน/เขียนข้อมูลจอง เส้นทางการแจ้งเตือนทางอีเมล ยังไม่เปิดใช้งาน

ลำดับเหตุการณ์เมื่อกด “ยืนยันการจอง”

ลำดับเกิดอะไรขึ้นทำงานที่ไหน
1ตรวจว่ากรอกชื่อ วันที่ และสาขาครบหรือยัง และวันที่ที่เลือกอยู่ในช่วงที่จองได้หรือไม่บนเครื่องผู้ใช้
2ตรวจว่าชื่อนี้จองวันนี้ไปแล้วหรือยัง และวันนั้นมีคนจองครบ 15 คนหรือยังบนเครื่องผู้ใช้
3ปิดปุ่มยืนยันชั่วคราว กันคนกดรัวจนได้คิวซ้ำบนเครื่องผู้ใช้
4ถ้าวันนั้นเต็มแล้ว ระบบถามว่าจะลงคิวสำรองไหม ถ้าเอาต้องกรอกอีเมลไว้สำหรับแจ้งเตือนบนเครื่องผู้ใช้
5เลือก Account Number จากเลขที่ว่างวันนั้น (มีชื่อเจ้าของจริงให้ดู และระบบแนะนำเลขที่ตรงชื่อเล่น/ชื่อเต็มให้ก่อน)บนเครื่องผู้ใช้
6ส่งข้อมูลการจองพร้อมรหัสลับ ไปยังตัวกลางที่ทำหน้าที่เขียนข้อมูลลงชีตส่งออกจากเครื่องผู้ใช้
7ตรวจรหัสลับ แล้วตรวจซ้ำในตัวล็อกกันชนว่าเลขที่เลือกยังว่างจริงไหม — ถ้าถูกคนอื่นชิงไปพอดี จะตอบกลับให้เลือกใหม่แทนที่จะปล่อยให้ซ้ำGoogle Apps Script
8หาแถวว่างถัดจากแถวข้อมูลจริงแถวสุดท้าย แล้วเขียนแถวใหม่ลงตรงนั้น พร้อมแสดงบัตรคิวขึ้นบนหน้าจอGoogle Apps Script
9ถ้าเป็นการลงคิวสำรอง (ไม่ใช่คิวจริง) ระบบจะส่งอีเมลแจ้งอัตโนมัติ — คิวที่ยืนยันตั้งแต่แรกไม่มีอีเมลอัตโนมัติ แต่กดขอให้ส่งเองได้ทีหลังn8n
10หน้าเว็บดึงข้อมูลใหม่จากชีตทุก 60 วินาที ทุกคนที่เปิดอยู่จึงเห็นคิวตรงกันบนเครื่องผู้ใช้

กันโค้ดแปลกปลอมที่แฝงมากับชื่อทุกอย่างที่ผู้ใช้พิมพ์เข้ามา จะถูกแปลงให้เป็นตัวอักษรธรรมดาก่อนนำไปแสดงบนหน้าเว็บเสมอ ถึงมีคนพิมพ์คำสั่งโปรแกรมใส่มา มันก็แค่แสดงเป็นข้อความ ไม่ทำงานใช้งานอยู่
ตรวจข้อมูลที่ดึงกลับมาจากชีตข้อมูลที่อ่านกลับมาจาก Google Sheets ถูกตรวจใหม่ทุกช่อง — ตัดข้อความที่ยาวผิดปกติ ล้างอักขระแปลก ๆ ออก และถ้าสถานะเป็นค่าที่ไม่รู้จักก็ดึงกลับเป็นค่าปกติ ต่อให้มีคนไปแก้ในชีตมั่ว ๆ หน้าเว็บก็ไม่พังใช้งานอยู่
ยืนยันตัวก่อนยกเลิกคิวคนที่จะยกเลิกคิวได้ต้องรู้ Account Number ของคิวนั้น คนอื่นจึงกดยกเลิกคิวแทนกันไม่ได้ใช้งานอยู่
กันการกดปุ่มรัวระหว่างที่รอเซิร์ฟเวอร์ตอบกลับ ปุ่มยืนยันจะถูกปิดไว้ กดกี่ครั้งก็ได้คิวเดียวใช้งานอยู่
ตรวจกฎอีกรอบก่อนบันทึกจริงระหว่างที่ผู้ใช้กรอกฟอร์มอยู่ อาจมีคนอื่นจองแทรกจนวันนั้นเต็มพอดี ระบบจึงตรวจกฎซ้ำอีกครั้งก่อนบันทึกใช้งานอยู่
ไม่มีรหัสผ่านหลุดในโค้ดที่ขึ้น GitHubไฟล์บอท Discord 2 ไฟล์ที่มี credential จริง (coworking-booking-bot.json, send-dm-intro-bot.json) ถูกใส่ไว้ใน .gitignore อย่างถูกต้องแล้ว จึงไม่ขึ้นไปอยู่บน repo สาธารณะ — รหัสจริงของ Gmail และ Google Sheets ก็เก็บอยู่ในระบบ n8n ไม่ได้อยู่ในไฟล์ที่ขึ้น GitHub เช่นกันตรวจแล้ว
ต้องมีรหัสลับถึงจะเรียกตัวกลาง (Apps Script) ได้ทุกคำขอไปยัง Apps Script ต้องแนบรหัสลับ ยิงตรง ๆ โดยไม่แนบจะถูกปฏิเสธทันที (ทดสอบจริงแล้ว ได้ค่า unauthorized กลับมา) กันบอท/สคริปต์ที่สุ่มยิง URL ตรง ๆ ได้ใช้งานอยู่
ตรวจ Account Number ซ้ำอีกรอบที่เซิร์ฟเวอร์ ก่อนยืนยันการจองใหม่ตอนกดยืนยันจอง เซิร์ฟเวอร์จะตรวจในตัวล็อกกันชน (LockService) ว่าเลขที่เลือกไว้ยังว่างจริงไหม ถ้ามีคนชิงไปพอดีจะปฏิเสธและให้เลือกใหม่ แทนที่จะปล่อยให้สองคนได้เลขเดียวกัน — ใช้กับ “การจองใหม่” เท่านั้นใช้งานอยู่

สูง Account Number ทั้ง 15 ชุด พร้อมชื่อเจ้าของจริง ฝังอยู่ในหน้าเว็บ ใครก็ตามที่เปิดหน้าเว็บ สามารถกดดูโค้ดของหน้าเว็บแล้วเห็นทั้งหมายเลขและชื่อ-นามสกุลจริงของเจ้าของทั้ง 15 คนได้ทันที — ยิ่งกว่าเดิมเพราะตอนนี้ตัวเลือก Account Number ต้องโชว์ชื่อให้ผู้ใช้ดูด้วย ผลคือเข้าใช้พื้นที่ได้โดยไม่ต้องจอง และเอาหมายเลขไปกดยกเลิกคิวของคนอื่นได้ด้วย แนวทางแก้: ย้ายการดึงรายชื่อไปทำที่ฝั่งเซิร์ฟเวอร์ แล้วส่งกลับมาเฉพาะรายการที่ยังว่างในวันนั้นเท่านั้น ไม่ต้องส่งทั้ง 15 รายชื่อมาให้ทุกคนเห็น
กลาง รหัสลับที่ใช้ป้องกัน Apps Script ก็ฝังอยู่ในหน้าเว็บเหมือนกัน รอบก่อนแนะนำให้เพิ่มรหัสลับ ตอนนี้เพิ่มแล้วจริง (ทดสอบแล้วว่ายิงไม่มีรหัสถูกปฏิเสธ) แต่ตัวรหัสเองเป็นค่าคงที่ในไฟล์ JavaScript ที่ทุกคนเปิดดูโค้ดหน้าเว็บได้ ตามคอมเมนต์ในโค้ดเองก็บอกว่าเป็นแค่การ “กันบอท/สแกนที่สุ่มยิง URL ตรง ๆ” — คนที่ตั้งใจเปิดโค้ดหาโดยเฉพาะยังคัดลอกรหัสไปยิงเองได้อยู่ดี แนวทางแก้: ยกระดับเป็นการยืนยันตัวตนจริง (เช่น ผูกกับบัญชีอีเมลบริษัท) ถ้าต้องการกันคนตั้งใจเจาะจริง ๆ
กลาง ระบบไม่รู้ว่าคนที่จองเป็นใครจริง ๆ ระบบเชื่อชื่อที่พิมพ์เข้ามาตรง ๆ ใครจะจองในชื่อใครก็ได้ และถ้าอยากจองซ้ำในวันเดียวกันก็แค่สะกดชื่อให้ต่างไปนิดเดียวก็ผ่านแล้ว แนวทางแก้: ให้ล็อกอินด้วยอีเมลบริษัทก่อนจอง ถ้าต้องการความรัดกุมขึ้น
กลาง ระบบส่งอีเมลอัตโนมัติ (n8n) เปิดรับคำสั่งจากใครก็ได้ ยังไม่ได้ตรวจสอบจุดนี้ในรอบทดสอบนี้ว่ามีการยืนยันตัวผู้เรียกไหม — ถ้ามีคนรู้ที่อยู่ของ webhook ก็อาจสั่งให้ส่งอีเมลออกจากบัญชีบริษัทได้ แนวทางแก้: ตั้งรหัสลับสำหรับเรียกใช้ และจำกัดจำนวนครั้งที่เรียกได้ต่อช่วงเวลา
กลาง การเลื่อนคิวสำรองขึ้นเป็นคิวจริง (ตอนมีคนยกเลิก) ยังจ่ายเลขที่ฝั่งเครื่องผู้ใช้อยู่ การ “จองใหม่” ตอนนี้ตรวจซ้ำที่เซิร์ฟเวอร์แล้ว แต่เส้นทาง “คิวสำรองได้เลื่อนเป็นคิวจริงเพราะมีคนยกเลิก” ยังคำนวณเลขที่จะให้ที่ฝั่งเบราว์เซอร์เหมือนเดิม ถ้ามีคนสองคนกดยกเลิกพร้อมกันเป๊ะ ๆ ในวันเดียวกัน อาจมีโอกาสจ่ายเลขซ้ำในจุดนี้ได้ (โอกาสเกิดต่ำ เพราะต้องมีคนยกเลิกพร้อมกันจริง ๆ) แนวทางแก้: ย้ายการจ่ายเลขในเส้นทางนี้ไปทำในตัวล็อกฝั่งเซิร์ฟเวอร์แบบเดียวกับการจองใหม่
กลาง ข้อมูลการจองถูกจำไว้ในเครื่องที่เปิดเว็บ ถ้าเป็นคอมพิวเตอร์ส่วนกลางที่ใช้ร่วมกัน คนที่มาใช้ต่อสามารถเปิดดูรายชื่อและ Account Number ของคนก่อนหน้าได้ แนวทางแก้: ล้างข้อมูลที่จำไว้เมื่อปิดหน้าเว็บ หรือเก็บเท่าที่จำเป็นต่อการแสดงปฏิทินเท่านั้น
ต่ำ หน้าเว็บดึงโค้ดจากภายนอกโดยไม่มีการจำกัด หน้าเว็บโหลดส่วนประกอบจากเว็บภายนอกสามแห่ง (ตัวจัดหน้าตา ปฏิทิน และชุดไอคอน) ถ้าแหล่งใดถูกแฮ็ก หน้าเว็บเราก็ได้รับผลกระทบตาม แนวทางแก้: ระบุรายชื่อแหล่งที่อนุญาต และตรวจลายเซ็นไฟล์ก่อนใช้งาน
ต่ำ ชื่อที่มีอักขระพิเศษอาจแสดงผลเพี้ยน รอบก่อนพบว่าระบบแปลงอักขระพิเศษสองรอบ (ตอนบันทึกและตอนแสดงผล) ทำให้ชื่ออย่าง “A&B” ขึ้นบนหน้าจอเพี้ยน — รอบนี้ยังไม่ได้ตรวจซ้ำว่าแก้แล้วหรือยัง เรื่องนี้ไม่ใช่ช่องโหว่ แค่ดูไม่สวย แนวทางแก้: เก็บชื่อตามที่ผู้ใช้พิมพ์ แล้วค่อยแปลงตอนแสดงผลเพียงรอบเดียว

ข้อมูลส่วนบุคคลที่ระบบเก็บ

  • ชื่อพนักงาน — ใช้ระบุว่าใครเป็นคนจอง และกันไม่ให้คนเดิมจองซ้ำในวันเดียวกัน
  • ทีม — ใช้ดูภาพรวมว่าแต่ละทีมใช้พื้นที่กันมากน้อยแค่ไหน (ตัดช่องบริษัทออกจากฟอร์มแล้ว ไม่เก็บข้อมูลนี้จากการจองใหม่อีกต่อไป)
  • อีเมล — เก็บเฉพาะคนที่กรอกเอง เพื่อส่ง Account Number ให้ และแจ้งเตือนเมื่อคิวสำรองได้คิว
  • ชื่อ-นามสกุลจริงของเจ้าของ Account Number ทั้ง 15 คน — เดิมเก็บไว้แค่ในทะเบียนอ้างอิง ตอนนี้ต้องแสดงให้ผู้จองทุกคนเห็นระหว่างเลือกเลขด้วย (ดูรายละเอียดในตารางความเสี่ยงด้านบน)
  • ทั้งหมดเก็บอยู่ใน Google Sheets ของบริษัท และตอนนี้ยังไม่ได้ตกลงกันว่าจะเก็บไว้นานแค่ไหน หรือจะลบข้อมูลเก่าเมื่อไร — ควรกำหนดให้ชัดเจน
